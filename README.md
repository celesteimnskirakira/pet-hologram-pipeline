# 宠物睡眠循环视频流水线

用户上传宠物正面照 → 生成纯黑背景正视图（严格保留原宠物特征）→ 生成 5 秒头尾循环的卧趴睡觉视频。

## 微雪 AMOLED USB 播放器

生成的视频可以通过配套 macOS 拖放工具直接发送到 **Waveshare ESP32-S3-Touch-AMOLED-1.75**，无需拔出 microSD：

- [下载与使用 Holo Video Uploader](holo-video-uploader/README.md)
- 拖入视频后自动转换为 360×360 / 10 FPS / MJPEG AVI
- USB 上传完成后立即 466×466 全屏循环播放
- 可在应用列表中选择并切换视频
- 可轮询团队后端接口，自动接收 MP4 并推送到微雪

实际是四步，中间多了一步睡姿桥接帧。原因见下面「为什么多了一步」。

视频用 Seedance 2.0 mini，走火山方舟官方通道，按当前促销价 **480p 1:1 一条约 0.44 元**。

## 快速开始

```bash
export ARK_API_KEY=你的火山方舟key

python cli.py doctor                    # 环境自检
python cli.py price                     # 成本对照表
python cli.py run 我家猫.jpg              # 跑完整三步
python server.py --port 8791            # 或者开网页上传界面
```

key 存放推荐用 `.env`（已在 `.gitignore` 里）：

```bash
cp .env.example .env     # 然后填入 ARK_API_KEY
python cli.py doctor     # 会告诉你 key 是从 .env 还是 shell 读到的
```

这样密钥不会进 shell 历史，也不用写到全局 rc 文件里。真实环境变量优先级更高，所以临时 `export` 可以覆盖文件。

依赖：Pillow、ffmpeg，扫码展台额外需要 segno（`pip3 install segno`），其余全走标准库。ffmpeg 缺失不会中断流水线，只会跳过循环接缝修整。

## 成本：怎么做到最便宜

方舟对 Seedance 按 token 计费，公式是官方给的：

```
tokens = (输入视频时长 + 输出视频时长) × 输出宽 × 输出高 × 帧率 / 1024
```

关键点在于**token 数只跟像素量有关**，所以选对分辨率和画幅就能直接砍成本。Seedance 2.0 系列刊例价（480p/720p 输出、输入不含视频）：

| 模型 | 元/百万 token | 当前促销 |
| --- | --- | --- |
| doubao-seedance-2-0 | 46.00 | 无 |
| doubao-seedance-2-0-fast | 37.00 | 75 折 |
| **doubao-seedance-2-0-mini** | **23.00** | **4 折（截至 2026-09-07 14:00）** |

5 秒 24fps 各档实际价格：

| 分辨率 | 画幅 | 像素 | tokens | 刊例 | 促销价 |
| --- | --- | --- | --- | --- | --- |
| **480p** | **1:1** | **640×640** | **48,000** | **1.104 元** | **0.442 元** |
| 480p | 4:3 | 752×560 | 49,350 | 1.135 元 | 0.454 元 |
| 480p | 16:9 | 864×496 | 50,220 | 1.155 元 | 0.462 元 |
| 720p | 16:9 | 1280×720 | 108,000 | 2.484 元 | 0.994 元 |

所以默认配置就是 480p + 1:1：同样 5 秒，比 720p 便宜一半多。mini 不支持 1080p 和 4K，那两档只有标准版有。

三个省钱细节：

1. **首帧图片先本地裁成正方形**，避免服务端居中裁剪把宠物裁掉，省掉重跑的钱。
2. **不传参考视频**。含视频输入虽然单价低（14 元/百万 token），但有最低 token 用量兜底，5 秒反而更贵。
3. 最终账单以 API 返回的 `usage.completion_tokens` 为准，流水线会把实际 token 数记进 `report.json` 的 `actual_cost`。

如果预算比稳定性更重要，也有第三方中转（APIPod 等）按秒计价、720p 特价约 $0.025/s。但那是非官方通道，稳定性和数据合规都要自己评估，本流水线默认不走。

## 第 2 步：怎么保证"严格保留宠物特点"

只靠一句"保持相似"是不够的，所以这里做了三层约束：

**一、先把特征抽成结构化文本。** 用视觉模型把上传照读成 17 个字段的 JSON：花色、斑纹、眼睛颜色、耳型、鼻头颜色、白袜子在哪只脚、有没有项圈、左右不对称特征等。真实测试里橘猫抽出来是这样：

```json
{
  "coat_pattern": "tabby",
  "primary_colors": ["orange", "white"],
  "markings": ["white muzzle", "white chin", "white chest", "white front paws"],
  "eye_color": "green",
  "nose_color": "pink",
  "ear_shape": "upright triangular"
}
```

**二、原图 + 特征清单一起送进图像模型。** 提示词里把这些特征列成"MUST MATCH"硬约束，再加一段禁止项：不许改花色、不许改眼睛颜色、不许加原图没有的项圈、不许卡通化。

**三、黑底做成可量化的验收标准。** 只采样画面外圈 6% 的边框区域算亮度（这样深色毛的宠物不会被误判），要求平均亮度 ≤ 12 且纯黑像素占比 ≥ 97%。不达标就带着"上次背景不够黑"的提示重试，最多 3 次，最后再做一次把近黑像素钳到纯 #000000 的确定性收尾。

真实调用里这个重试是有用的——第一次背景亮度 14.0 没过，重试一次降到 1.79：

```
[still_scored] attempt=1 mean_luma=14.042 black_ratio=0.8463
[still_scored] attempt=2 mean_luma=1.787  black_ratio=0.984
[still_final]            mean_luma=1.707  black_ratio=0.9842
```

## 第 3 步：怎么做到头尾循环

**主要手段是首尾同帧。** 方舟的图生视频支持 `first_frame` 和 `last_frame` 两个 role，官方明确说这两张可以传同一张图。把睡姿图同时当首帧和尾帧送进去，模型就被约束成“从这个姿态出发、回到这个姿态”。

**其次是把运动压到最低。** 睡觉这个场景天然适合循环：提示词只允许呼吸起伏（整段约两次完整呼吸）和极轻微的耳朵抖动，锁死机位（`--cf true`），眼睛全程闭着，不许抬头、不许起身、不许睁眼。负向提示词再兜一层：镜头运动、转场、花色漂移、水印全部排除。

**最后用 ffmpeg 做客观验收和修整。** 扩散模型只会"接近"开头姿态，而且尾帧本身重复会造成一帧卡顿。所以流水线会抽出首帧和末帧算平均绝对差，给出 seamless / good / visible / poor 评级，然后修整：

- `trim`（默认）：裁掉重复的尾帧，消除播放循环时的卡顿。
- `xfade`：把尾段交叉淡化到开头，模型飘得比较远时用这个，代价是片长略短。
- `none`：不处理，只出度量报告。

修整前后各测一次，两个数都写进 `report.json`，循环质量是可核查的而不是靠感觉。

## 为什么多了一步睡姿桥接帧

最初的设计是把黑底正视图（坐姿、睁眼）直接当首尾帧丢给视频模型，实测下来不行：出来的片子猫仍然坐着、眼睛睁着，根本没有睡觉。

原因是两个约束在打打。首尾帧在说“保持这个样子”，提示词在说“躺下来睡觉”，而前者是像素级的硬约束，能轻松压过文本。让模型从坐姿重构到卧趴睡姿，本身就是个大幅度姿态变化。

所以把姿态变化挪到图像空间完成：先用图像模型从正视图生成一张已经睡着的黑底图，再拿它去做首尾帧。这样视频模型只需要加呼吸，不需要重构姿态，两个约束方向一致了。改完之后实测就对了。

正视图作为你要的交付物保留，桥接帧只是中间产物。想回到老行为用 `--no-sleep-bridge`。

## 为什么要单独测“动没动”

接缝指标有个坑：一段完全静止的视频，首尾天然完全一致，会拿到完美的 `seamless` 评级。所以光看接缝会把“模型啥都没生成”当成成功。

`measure_motion` 抽取片中多帧跟首帧对比，阈值是拿真实数据标定的：同规格完全冻结的 h264 片子测出 0.007，真实生成的呼吸片子测出 约 2.0，相差近 300 倍，所以 0.3 以下当编码噪声。

这个指标的能力边界要说清楚：它只能告诉你画面动没动，告诉不了你姿态对不对。一只坐着睁眼、但毛发微微浮动的猫，得分跟一只正确睡着的猫一样。姿态对不对还是得看帧。

## 路演现场模式

面向全息投影展台：访客扫码上传→后台并行生成多个动作→亚克力板下的屏幕循环播放。

```bash
python display.py --port 8792 --lan
```

`--lan` 是扫码的前提：不加它只绑 127.0.0.1，手机连同一个 WiFi 也访问不到。启动后终端会打印访客链接，开控制台右上角的“二维码”就能直接给访客扫。

三个页面：

- `/u?k=...` 访客页（手机）：选照片、填宠物名、选睡姿，提交后看四段进度，完成后能在手机上先看一眼。
- `/` 操作台（展台笔记本）：看队列和每位访客的进度，也可以自己上传，完成后点“投到屏幕”。
- `/stage` 投影页：铺在亚克力板下的屏幕上，全屏。纯黑无 UI。

- `/` 操作台：上传、选动作组合、看队列和每位访客的进度，完成后点“投到屏幕”。
- `/stage` 投影页：铺在亚克力板下的屏幕上，全屏。纯黑无 UI，双视频层交叉淡化切换动作。

新完成的宠物会自动上屏，所以常规流程不需要手动干预。

### 扫码的安全边界

访客链接带一个每次启动随机生成的 token，没有它 `/u` 和上传接口都返回 403。这模拟的是“扫了码才能用”，让访客无需输入任何东西，同时避开路人矎到 IP 就能刷接口。重启服务会换 token，旧二维码失效，所以**展前少重启，或者重启后重新投二维码**。

两个得知道的局限：控制台（`/`）**没有** token 保护，局域网内任何人矎到它都能操作展台；token 走 URL 参数且是纯 HTTP，同网段拓扑下可被嗅探。所以建议用**自己的手机热点**而不是会场开放 WiFi。这是展位级防护，不是公网级防护。

### 黑底在这里不是审美，是功能

佰普尔幻象（Pepper's ghost）里亚克力只反射亮部，黑色不发光等于透明，宠物才会看起来悬浮在空中。所以流水线的黑底检测是硬指标：任何不够黑的边缘都会在现场反射成一个可见的发亮矩形。

渲染时做了三件事：

1. **镜像翻转**。单面 45° 反射会左右镜像，不预先翻转的话，猫的白爪子会跑到错的一侧 —— 而那恰好是主人最先看的细节。
2. **压黑**。面板背光泄漏会反射成难气，把近黑像素钳到纯 0 能明显改善悬浮感。
3. **留边**。主体不能碰到板子边缘，那里反射几何会失真。

四面锥形结构用 `--rig quad`：把画面拼成四份、各自旋转、脚朗外，一块平铺屏幕就能喘四个方向。

这一块我写错了三次：前两版用 ffmpeg filtergraph，一次因为 `color` 源没设时长而无限挂住，一次因为 `transpose` 会交换宽高导致四份被裁。最终改成 Pillow 逐帧合成 —— 坐标能精确控制，正确性比紧凑重要。

### 多动作并行与限流

默认生成三个视觉差异明显的睡姿（侧卧蜷睡 / 趴卧收爬 / 侧身伸展），屏幕循环切换，看起来是变化而不是卡顿。

并行这里有一个坑我实测才发现：**视频任务提交有每账号限流**。最初同时发 3 个，后两个直接 429 被拒，3 个只成 1 个。现在的做法是只串行化提交这一下，轮询仍然重叠 —— 因为等待时间几乎全在轮询上，所以并行依然有效。遇到 429 会自动等待重试而不是丢掉动作。

各通道测到的限制：

| 通道 | 提交限制 | 默认间隔 |
| --- | --- | --- |
| Ark（个人） | 3 并发 | 0 秒，背靠背提交 |
| Agnes | 1 个 / 分钟 | 62 秒 |

实测耗时（Agnes，带 62 秒限流）：2 个动作 173 秒。**换成 Ark 会快很多**，因为 3 个动作可以同时提交，总时长接近单个动作。

### 现场节奏建议

你的安排（先上传、再讲 2-3 分钟产品、然后看结果）正好匹配这个耗时，而且比干等体验好。几个配合的细节：

队列是单线程串行的，所以多人陆续上传不会相互拖慢，但第二位要等第一位跑完。若一批讲解时有三四位访客，建议每人只选两个动作。

建议提前准备几只演示宠物先跑好存着，万一现场网络或 API 出问题，随时能点“投到屏幕”应急。

可以先用 `python cli.py doctor` 确认环境（尤其是代理，这个坑我踩过）。

## 已验证 / 未验证

**已用真实 API 跑通全链路**：照片校验 → 特征抽取 → 黑底正视图（含背景不达标自动重试）→ 睡姿桥接帧 → 5 秒循环视频。成品：640×640、120 帧、5.0 秒整，接缝 `seamless`（0.734），运动 `subtle`（peak 1.976），抽帧确认侧卧趴睡、眼睛闭着、橘色虎斑纹和白爪都保留。

**路演模式也已实跑**：两个动作并行生成全部成功（173 秒，含 62 秒限流等待），接缝均 `seamless`，全息版边缘纯黑达标，抽帧确认镜像翻转方向正确。四面锥形模式单独验证过布局：四份完整、不重叠、脚朗外。

不过这次实跑走的是 Agnes 备用通道（本机只有 `AGNES_API_KEY`），**不是 Seedance**。

**已用合成视频验证**：接缝度量、运动检测（含冻结片子的噪声基线标定）、裁尾、交叉淡化、GIF 预览、限流重试与提交限速、TLS 中断后的轮询恢复、黑底误判回归、multipart 解析、完整编排。共 66 个测试全绿，视频相关的用 ffmpeg 真实合成片子跑过。

**未验证**：Seedance 2.0 mini 的实际调用。请求体是按官方文档构造的，含首尾帧 role 和 `--rs/--rt/--dur/--cf` 参数，但没有 key 无法实证。配好后建议先 `--dry-run` 看成本，再跑一条 480p。

**一个度量盲区**：接缝和运动两个指标都管不了姿态对不对。最开始那段坐姿睁眼的废片就拿到了 `seamless` + 非静止，是看帧才发现的。所以流水线会存 `preview_loop.gif`，首跑建议看一眼。

**黑底判定曾经误判大体型宠物**：旧逻辑量画面外圈 6% 的亮度，但构图饫满时宠物会延伸到底边，于是量到的是猫毛而不是背景 —— 宠物越大越容易被误判，方向是反的。现在先定位主体包围盒，只量盒外的像素。实测：之前要重试两三次的图现在第一次就过，全程从 300+ 秒降到 103 秒。

**全息结构的参数需要现场标定**：默认按单面 45° 做左右镜像。如果你的屏幕是平铺在板子下方而非竖置，可能还需要垂直翻转（`HologramSpec.flip_vertical`）。这个我无法隐形验证，现场拿一只演示宠物试一下就能定下来。
